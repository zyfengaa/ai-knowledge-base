# Qwen3-TTS 网络结构深度解剖

> 阿里通义（Qwen 团队）出品 | 全栈开源 TTS 模型家族 | 97ms 流式首包
> 2026 年 1 月发布 | Apache 2.0 | 0.6B / 1.7B 双规格

---

## 写在前面：Qwen3-TTS 的定位

Qwen3-TTS 是阿里 Qwen 团队在 2026 年初发布的全栈开源 TTS 模型家族。与 CosyVoice（同属阿里但不同团队）的区别：

| 维度 | CosyVoice 系列 | Qwen3-TTS |
|------|---------------|-----------|
| 所属 | FunAudioLLM（通义实验室） | **Qwen 团队** |
| 路线 | LLM + Flow Matching | **离散多码本 LM（纯 token 预测）** |
| 规格 | 300M-500M | **0.6B / 1.7B** |
| 核心优势 | 方言覆盖、零样本克隆 | **97ms 延迟 + VoiceDesign** |
| 生态 | HuggingFace + ModelScope | **HuggingFace + PyPI (`pip install qwen-tts`)** |

---

## 一、整体架构设计哲学

### 核心思想

> **"不需要扩散也不需要 Flow——离散 token 预测 + 轻量 CNN 解码就够了。"**

Qwen3-TTS 走了一条与其他 2024-2026 TTS 截然不同的路：

| 路线 | 代表 | 生成方式 |
|------|------|---------|
| **连续生成** | CosyVoice / F5-TTS | Flow Matching 在连续空间生成 |
| **离散 LM + 扩散** | Bark | LM 预测 token + 神经编解码器 |
| **离散 LM + CNN 解码** | **Qwen3-TTS** | LM 预测 token + 轻量 CNN 直接解码 |

Qwen3-TTS 的推理认为：扩散/Flow 在 TTS 中的角色已经过时了——如果 LM 能直接预测高质量的离散语音 token，为什么还需要中间加一个 ODE solver？

### 架构总览

```
文本 (10 种语言)
    │
    ├── ① Qwen3 多语言 Tokenizer
    │
    ├── ② 离散多码本 LM
    │   ├── 16 层 RVQ (残差矢量量化)
    │   ├── 第 1 层: 语义 token
    │   └── 第 2-16 层: 声学 token
    │
    ├── ③ 轻量 CNN 解码器
    │   └── token → 波形 (一步到位)
    │
    └── 波形: 24kHz
```

## 二、各模块深度解剖

### 2.1 Qwen3-TTS-Tokenizer（音频编解码器）

**定位**：将 24kHz 音频压缩为 16 层 RVQ 离散 token。参考 Mimi 架构设计。

```
输入: 24kHz 波形 [batch, T_audio]
    │
    ├── 因果编码器 (全卷积, 无 look-ahead)
    │   ├── 下采样: 16kHz → 12.5Hz (1280× 下采样)
    │   ├── 全因果——不依赖未来帧
    │   └── 输出: [batch, D, T_frame] @ 12.5Hz
    │
    ├── RVQ (Residual Vector Quantization) × 16 层
    │   ├── 第 1 层: 语义 → 量化残差最粗糙的部分
    │   ├── 第 2-16 层: 声学细节 → 逐层量化残差
    │   └── 每层码本大小: 1024 (10-bit)
    │
    └── 输出: [16, T_frame] 离散 token 矩阵
```

| 参数 | 值 | 含义 |
|------|-----|------|
| 帧率 | **12.5Hz** | 每秒 12.5 帧 token |
| RVQ 层数 | **16** | 比 EnCodec (8) 多一倍 |
| 每码本大小 | 1024 | 10-bit |
| 每帧信息量 | 16 × 10 = 160 bits | 比 EnCodec 的 80 bits 多一倍 |
| Tokenizer PESQ | **3.21** | Mimi: 2.88——重建质量领先 |
| Tokenizer SIM | **0.95** | 音色近乎无损保留 |

**为什么 16 层？** 
- 语义层（第 1 层）: 编码"说什么"
- 中 4 层（第 2-5 层）: 编码"说的语气/基频轮廓"
- 后 11 层（第 6-16 层）: 编码"声学细节/音色特征"

前几层信息"更语义"，后几层"更声学"。这种分级在训练 LM 时可以通过预测不同层的 token 来分离"理解"和"生成"难度。

### 2.2 离散多码本 LM

**定位**：Qwen3-TTS 的核心。用纯语言模型预测 16 层 RVQ token。

#### 模型规格

| 规格 | 参数量 | Hidden Size | 层数 | 最小显存 |
|------|--------|------------|------|---------|
| **0.6B** | ~600M | 1024 | 16 | ~3.5-4GB |
| **1.7B** | ~1.7B | 2048 | 28 | ~5-6GB |

#### 输入输出

```
输入: 文本 token + 说话人 prompt token
    │
    ├── Qwen3 LM (Causal Transformer)
    │   ├── RoPE 位置编码
    │   ├── GQA (分组查询注意力)
    │   └── SwiGLU FFN
    │
    └── 输出: 16 层 RVQ token 的预测概率

推理时:
  - 自回归预测第 1 层（语义 token）
  - 基于第 1 层 + 上下文 > 预测第 2 层
  - ... 逐层递进 → 完整 16 层 token 矩阵
```

**为什么是 12.5Hz 这么低的帧率？**

```
12.5Hz × 1 秒 = 12.5 帧 × 16 层 RVQ = 200 token/秒

对比:
  EnCodec (Bark): 75Hz × 8 层 = 600 token/秒
  低帧率的优势: 自回归步数更少 → 推理更快
  低帧率的挑战: 每帧信息量更大 → LM 需要更强的预测能力
```

**多 Token 预测（MTP）模块**：Qwen3-TTS 的 LM 在预测当前 token 时，也同时预测后续 2-3 个 token 的粗略分布。这减少了自回归步数：

```
标准自回归:
  Step 1: 预测 token_1
  Step 2: 用 token_1 预测 token_2
  Step 3: 用 token_1+2 预测 token_3

MTP (Qwen3-TTS):
  Step 1: 预测 token_1 + 粗略预测 token_2, token_3
  Step 2: 用 token_1 + token_2_draft 预测 token_2_fine + ...
  → 约 2x 加速
```

### 2.3 轻量 CNN 解码器

**定位**：16 层 RVQ token → 24kHz 波形。一步到位，不经过 Mel 频谱。

```
输入: [16, T_frame] 离散 token 矩阵
    │
    ├── Token Embedding: 16 × 1024 → 16 × D
    ├── 拼接: [T_frame, 16 × D]
    │
    ├── 轻量卷积解码器
    │   ├── Conv1D (上采样 1280×)
    │   ├── 16× 到 12.5Hz × 1280 = 16kHz
    │   └── 最终输出: [1, T_audio]
    │
    └── 输出: 24kHz 波形
```

**为什么用 CNN 而不是 HiFi-GAN？** CNN 解码器是全卷积的——一次前向完成，不需要自回归。而 HiFi-GAN 虽然也很快，但它的架构是为"Mel→波形"优化的，不是为"RVQ token→波形"设计的。Qwen3-TTS 的 Tokenizer 直接输出高质量波形表征，CNN 解码器只需要做"上采样+平滑"——参数少、推理快。

### 2.4 VoiceDesign（音色设计）

**定位**：从自然语言描述直接创造新声音——不需要任何参考音频。

```
用户输入: "略带紧张的 17 岁男生，音域偏高"
    │
    ├── Qwen3 理解文本 → 提取声音属性
    ├── 属性 → 说话人嵌入 (128-D)
    │
    └── 说话人嵌入注入 LM → 生成对应音色的语音
```

| 测试 | Qwen3-TTS | MiniMax Voice Design (商业) |
|------|-----------|----------------------------|
| InstructTTS-Eval | **84.1 / 81.8** | — |
| 功能 | ✅ 开源可用 | ❌ 闭源 |
| 声音控制 | 年龄/性别/音域/情感 | 同上 |

## 三、推理流程演练（97ms 首包）

以生成 "今天天气真不错" 为例：

### Non-streaming 模式

```
Step 1: 文本 "今天天气真不错" → Tokenizer → 6 个 token
Step 2: LM 预测 16 层 RVQ token
    └── 6 帧 × 16 层 = 96 token 自回归
Step 3: CNN 解码 → 波形

总延迟: ~200ms (包含完整文本处理)
```

### Streaming 模式（Dual-Track）

```
Step 1: 用户输入前 5 个字 "今天天气真" → ~0.3s 输入
Step 2: LM 预测首批 token (仅需 1-2 帧) → ~20ms
Step 3: MTP 模块预判后续 → ~10ms
Step 4: CNN 解码首批波形 → ~50ms
Step 5: 开始播放 → ~17ms 缓冲

首包延迟: 97ms ← 行业首个破 100ms 的开源 TTS
后续: 边播边生成 (流式播放) → 无额外感知延迟
```

### 延迟分解（Streaming）

```
┌──────────────┐
│ 文本输入 ~300ms│  ← 用户打字/语音识别时间
├──────────────┤
│ LM 预测 ~20ms │  ← 首批 token (MTP 加速)
├──────────────┤
│ CNN 解码 ~50ms│  ← 首批波形
├──────────────┤
│ 缓冲 ~17ms    │  ← 启动播放器
├──────────────┤
│ 总延迟 ~97ms  │  ← 从"输入够 5 个字"到"听到声音"
└──────────────┘
     <── 100ms 门槛 人耳几乎无感知
```

## 四、Qwen3-TTS 性能指标

| 评测 | Qwen3-TTS 1.7B | 同期最佳 | 含义 |
|------|:---:|:---:|------|
| **首包延迟** | **97ms** | 150ms (CosyVoice 2) | 首个破 100ms 的开源 TTS |
| Tokenizer PESQ | **3.21** | 2.88 (Mimi) | 重建质量最高 |
| 说话人相似度 | **0.95** | 0.87 (CosyVoice 2) | 近乎无损保留 |
| 中文 WER | **0.77%** | 0.71% (CosyVoice 3) | 非常接近 |
| 跨语种克隆 WER (中→韩) | **4.82%** | 14.4% (CosyVoice 3) | 大幅领先 |
| 长文本 WER (10min 英) | **2.81%** | 3.2% (Fish Speech S2) | 长文本稳定性好 |
| VoiceDesign | **✅ 开源唯一** | MiniMax (闭源) | 唯一开源实现 |

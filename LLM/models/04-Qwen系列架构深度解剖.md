# Qwen 系列架构深度解剖

> Alibaba | Qwen → Qwen2 → Qwen2.5 → Qwen3 —— 中文开源大模型最完整的家族谱系

---

## 写在前面

Qwen（通义千问）系列的价值用一句话概括：

> **"LLaMA 级别的工程功底 + 原生中文优化 + Apache 2.0 开源 + 全尺寸覆盖 = 全球最完整的开源大模型家族之一。"**

从 2023 年 9 月 Qwen-7B 首次发布，到 2026 年 Qwen3 系列全线铺开，Qwen 在不到三年的时间里迭代了四个大版本，覆盖从 **0.5B 到 236B MoE** 的完整参数谱系，所有模型均使用 Apache 2.0 许可证。据沙利文/头豹研究院 2025 下半年的数据，Qwen 在中国企业级大模型市场份额达到 **32.1%**，是所有中文 LLM 提供商中最高的。

这条演进路径——从对齐 LLaMA 到超越 LLaMA，再到自成一派的完整技术栈——是 LLM 后发者如何通过系统性工程追上并领先的典型案例。

## 第一章 前置条件：Qwen 之前的中文开源 LLM 格局

### 1.1 LLaMA 的中文困境

2023 年初，Meta 发布 LLaMA 系列（244GB 语料 = 1.4T tokens），成为开源 LLM 的事实标准。但 LLaMA 有一个对中文社区来说致命的弱点：

```
LLaMA tokenizer 词表大小: 32K

中文文本的编码效率:
  "中华人民共和国" → LLaMA: 7-9 tokens
                      Qwen:   3-4 tokens

原因: LLaMA 的 BPE tokenizer 主要基于英文语料训练
      — 中文字符在英文语料中出现的频率极低
      — BPE 合并策略不会为中文"常用字/词"分配单独的 token
      — 单个中文字 ≈ 1 token, 但常见中文双字词被拆成 2-3 token
      而英文 "the" 只需要 1 token
```

这意味着用 LLaMA 处理中文，**推理成本比英文高 2-3 倍**（同等 token 预算下能处理的中文信息量只有英文的 1/2 到 1/3），而且中文能力来自"意外"——LLaMA 的训练数据里中文占比极低（<5%），中文理解本来就是副产品。

### 1.2 碎片化的中文开源生态

2023 年上半年，中文开源 LLM 的格局是这样的：

- **ChatGLM-6B**（智谱，2023.03）：6B 参数，中文友好，但基于 GLU 架构，与主流 LLaMA 生态不兼容
- **MOSS**（复旦，2023.04）：有想法但规模小，维护力度不足
- **Baichuan-7B/13B**（百川，2023.06）：Apache 2.0，质量不错，但模型家族规模有限
- **Chinese-LLaMA-Alpaca**（社区项目）：在 LLaMA 上做增量预训练 + 词表扩展，非官方维护

这些模型各自为战，没有形成统一的生态。开发者如果需要一个**完整的模型家族**（小模型做微调、大模型做推理、多模态变体、持续更新），几乎没有选择。

### 1.3 Qwen 的机会窗口

阿里巴巴看到了这个空白：

1. **中文原生优化**：从 tokenizer 到训练数据全部以中文为核心
2. **全尺寸覆盖**：0.5B ~ 236B，覆盖所有部署场景
3. **Apache 2.0**：最开放的许可证，无商用限制
4. **持续迭代**：Qwen → Qwen2 → Qwen2.5 → Qwen3，每代都有架构改进
5. **多模态原生**：从 Qwen 开始就同步发布 Audio/VL 变体，不是后加

这是一个经典的"系统性工程"策略——不是单点突破，而是在所有维度上同时输出高质量产品。

## 第二章 Qwen（2023 年 9 月，Apache 2.0）

### 2.1 首次亮相

Qwen 最初发布了三个规模：

| 模型 | 参数量 | 上下文长度 | 许可 |
|------|--------|-----------|------|
| Qwen-7B | 7B | 32K | Apache 2.0 |
| Qwen-14B | 14B | 32K | Apache 2.0 |
| Qwen-72B | 72B | 32K | Apache 2.0 |

同时发布的还有 **Qwen-Audio**（语音多模态）和 **Qwen-VL**（视觉多模态），表明 Alibaba 从一开始就规划了一个完整的模型生态，而不是只做一个纯文本模型。

### 2.2 架构

Qwen 的基本架构是 **Decoder-only Transformer**，但已经搭载了当时最先进的设计选择：

```
Qwen Block 架构 (Decoder Layer):

输入 x
    │
    ├─ RMSNorm
    │      │
    │      └─ GQA (分组查询注意力)
    │           │
    │           ├─ Q 投影: [batch, seq_len, n_Q_heads × head_dim]
    │           ├─ K/V 投影: [batch, seq_len, n_KV_heads × head_dim]
    │           ├─ RoPE 位置编码
    │           ├─ Attention(Q, K, V) → softmax(Q·Kᵀ/√d) · V
    │           └─ 输出投影
    │
    ├─ 残差连接 +
    │
    ├─ RMSNorm
    │      │
    │      └─ SwiGLU FFN
    │           │
    │           ├─ 门控分支: x · W_gate  → Swish 激活
    │           ├─ 值分支:   x · W_up
    │           ├─ 逐元素相乘: Swish(x·W_gate) ⊙ (x·W_up)
    │           └─ 输出投影: 结果 · W_down
    │
    └─ 残差连接 → 输出
```

**几个关键设计选择：**

| 组件 | Qwen 的选择 | 对比 LLaMA | 为什么重要 |
|------|------------|-----------|-----------|
| **归一化** | **RMSNorm**（Pre-Norm） | 同样是 RMSNorm Pre-Norm | 去掉 LayerNorm 的均值计算，更高效；Pre-Norm 比 Post-Norm 训练更稳定 |
| **激活函数** | **SwiGLU** | SwiGLU（LLaMA 2 起） | 门控机制比 ReLU 有更强的表达能力；但需要 3 个权重矩阵（gate/up/down）而不是 2 个 |
| **注意力** | **GQA**（7B: 28Q/4KV, 72B: 64Q/8KV） | MHA（LLaMA 1）/ GQA（LLaMA 2 70B） | 推理时 KV Cache 减少到 MHA 的 1/N（N=GQA ratio），显存省 50-75% |
| **位置编码** | **RoPE** | RoPE | 相比固定正弦位置编码，RoPE 通过旋转矩阵编码相对位置，可以外推到一定长度之外 |
| **词表大小** | **152K** | 32K | 中文编码效率远超 LLaMA |

### 2.3 中文 Tokenizer 优化——Qwen 的"隐藏王牌"

Qwen 的 tokenizer 是其最被低估的技术优势之一：

```
LLaMA tokenizer 处理中文:
  "北京市朝阳区" → ["北", "京", "市", "朝", "阳", "区"] (6 tokens)
  "人工智能" → ["人", "工", "智", "能"] (4 tokens)

Qwen tokenizer 处理中文:
  "北京市朝阳区" → ["北京市", "朝阳区"] (2 tokens)
  "人工智能" → ["人工智能"] (1 token)

差异原因:
  - Qwen 词表大小 152K (vs LLaMA 32K)
  - 预训练数据中中文占主导 → BPE 合并时将中文常见词优先合并
  - 覆盖了大部分常用中文字词 (基于大规模中文语料统计)
```

**实际影响**：在同等 token 预算下，Qwen 可以"看到"的中文信息量是 LLaMA 的 2-3 倍。这意味着：
- 推理速度更快（更少的 token 需要生成）
- KV Cache 更小（更少的 token 长度）
- 对中文语义的理解更深（模型能在单个 token 级别看到完整的词，而不是碎片化的字）

### 2.4 训练数据

Qwen 在 **3 万亿 token** 的多语言数据上训练，其中中文占较大比重。数据涵盖：
- 网页文本
- 书籍
- 代码
- 多语言平行语料

与 LLaMA 的核心差异：中文不是"附加"的，而是从数据配比到 tokenizer 都以中文为核心设计的。

## 第三章 Qwen2（2024 年，Apache 2.0）

### 3.1 模型矩阵扩容

Qwen2 在 Qwen 的基础上大幅扩展了模型尺寸覆盖：

| 模型 | 参数量 | 架构 | 上下文 | 发布时间 |
|------|--------|------|--------|---------|
| Qwen2-0.5B | 0.5B | Dense | 128K | 2024 |
| Qwen2-1.5B | 1.5B | Dense | 128K | 2024 |
| Qwen2-7B | 7B | Dense | 128K | 2024 |
| **Qwen2-57B-A14B** | 57B (14B active) | **MoE** | 128K | 2024 |
| Qwen2-72B | 72B | Dense | 128K | 2024 |

**关键变化**：
1. 新增 **0.5B/1.5B** 小模型，面向端侧部署
2. 新增 **57B-A14B MoE** 混合专家变体，首次在 Qwen 家族引入 MoE 架构
3. 上下文长度从 **32K → 128K**（4 倍扩展）

### 3.2 三项核心技术改进

#### 3.2.1 YARN（Yet Another RoPE extensioN）

标准 RoPE 有一个已知问题：**长度外推能力有限**。在 32K 长度上训练的模型，直接推理 128K 序列时性能会大幅下降。

YARN 的思路很直观：

```
标准 RoPE 在位置 p 对维度 i 的旋转频率:
  θ_i = 10000^(-2i/d)

问题: 在训练长度 (32K) 内, θ_i 能很好地编码位置信息
      但超出训练长度后, 某些维度的"波长"不够长
      无法覆盖整个序列范围

YARN 的调整:
  对每个维度 i 的频率应用一个缩放因子 s_i:
    θ'_i = θ_i · s_i

  其中 s_i 的设计原则:
    - 低频维度 (i 小, 波长长) → 缩放小 (保留位置细节)
    - 高频维度 (i 大, 波长短) → 缩放大 (适应更长距离)
    - 整体调整使得"最长波长"能够覆盖 128K 的位置范围

  实际做法: YARN = NTK-aware scaling (通过调整频率
  而非直接线性插值, 保留高频维度的位置分辨率)
```

**不需要重训练**——YARN 是一个推理时的位置编码调整方法。Qwen2 将 YARN 与 **少量长上下文续训**（比如几千步 128K 序列的训练）结合，实现了从 32K 到 128K 的稳定扩展。

#### 3.2.2 Dual Chunk Attention（DCA）

DCA 是 Qwen2 实现 128K 高效训练的关键。标准 Full Attention 的计算复杂度是 O(n²) —— 对 128K 序列来说，这意味着 163 亿次注意力计算（128K² ≈ 1.6×10¹⁰），显存完全不可接受。

```
Dual Chunk Attention:

输入序列 (长度 L = 128K)
    │
    ├── 分块: 将 L 分成 M 个 chunk, 每块大小 C
    │   例: C = 8K, M = 16 (128K / 8K = 16)
    │
    ├── Step 1: 块内注意力 (Intra-Chunk Attention)
    │   ┌─────────────────────────────────────────┐
    │   │ Chunk_1: Self-Attn(8K) → O(C²)          │
    │   │ Chunk_2: Self-Attn(8K) → O(C²)          │
    │   │ ...                                      │
    │   │ Chunk_16: Self-Attn(8K) → O(C²)         │
    │   └─────────────────────────────────────────┘
    │   复杂度: M × O(C²) = O(L·C) = O(128K × 8K)
    │
    ├── Step 2: 跨块注意力 (Cross-Chunk Attention)
    │   只在特定层（比如每隔 N 层）执行一次全局跨块注意力
    │   或者在层内用滑动窗口 + 全局 token 的方式
    │
    └── 结果: 大部分计算在块内 (近似线性), 全局交互由少量跨层计算兜底
```

**复杂度分析**：

| 方法 | 计算复杂度 | 128K 序列的实际开销 |
|------|-----------|-------------------|
| Full Attention | O(L²·d) | 1.6×10¹⁰ × d |
| DCA (C=8K) | O(L·C·d) + O(L²·d)/N_layer | ~1.0×10⁹ × d（约 1/16） |
| 节省比例 | — | **~94% 的计算量减少** |

DCA 不是近似注意力——它是精确注意力的一种高效实现方式，利用了"大部分语义关联是局部的"这一先验知识，只在必要时才做全局交互。

#### 3.2.3 MoE 变体：Qwen2-57B-A14B

Qwen2 的 **Mixture of Experts** 变体是一个关键的技术验证：

```
Qwen2 MoE 配置:
  总参数量: 57B
  激活参数量: 14B (每 token 激活)
  专家数量: 16
  每 token 激活的专家数: 4 (top-4 routing)
  专家类型: Fine-grained experts (细粒度专家)

推理时的计算量相当于 14B 模型
但参数量有 57B, 知识容量更大

路由机制:
  每个 token 的 hidden state → Router 网络
    → 计算与 16 个专家的匹配分数
    → 选择 Top-4 专家
    → 4 个专家的输出加权求和

辅助损失:
  - 负载均衡损失 (Load Balancing Loss)
    - 鼓励 token 均匀分布在所有专家上
    - 防止路由 collapse (所有 token 都选同一个专家)
  - 专家 dropout 和随机路由 (训练时)
```

这个 57B-A14B MoE 是后来 Qwen2.5 的 110B 和 236B MoE 的前身和验证。

### 3.3 数据质量升级

Qwen2 对训练数据做了大幅质量提升：
- 更严格的 **去重**（MinHash + 精确去重）
- **质量过滤**（基于分类器打分，过滤低质量网页）
- **数据配比优化**（增加代码和数学比例）
- 训练数据总量上升到 **数万亿 tokens**

### 4.2 QwQ-32B：推理模型

QwQ-32B 是 Qwen2.5 中最引人注目的成员：

```
QwQ-32B 的核心能力: 让模型在回答之前进行"思考"

训练方法:
  1. 基础模型: Qwen2.5-32B
  2. 强化学习 (RL) 训练
     - 过程奖励模型 (PRM): 对推理过程中的每一步打分
     - 结果奖励模型 (ORM): 对最终答案的正确性打分
     - GRPO (Group Relative Policy Optimization):
       在同一问题的多个采样输出之间做相对优化
  3. 长链思维 (Long Chain-of-Thought) 数据
     - 数学推理: GSM8K, MATH, AIME
     - 编程: Codeforces, LiveCodeBench
     - 通用推理: 逻辑谜题, 科学推理

关键结果（2025 年初的数据）:
  - AIME 2024: 接近 DeepSeek-R1 的水平
  - MATH-500: 超过 R1-32B
  - 32B 参数实现了接近 671B MoE 的推理性能
```

QwQ-32B 的意义在于：证明**推理能力可以通过 RL 单独训练出来**，不需要扩大模型本身。32B 的 QwQ 在推理任务上碾压了 72B 甚至更大尺寸的非推理模型。

### 4.3 Agent 原生能力

Qwen2.5 是第一个**将 Agent 能力作为原生特性**的版本：

```
Qwen2.5 Agent 原生支持:

1. 工具调用 (Tool Calling)
   - 模型可以输出结构化工具调用请求
   - 内置支持: 搜索引擎、计算器、API 调用
   - 格式: 对话中嵌入 <tool_call> 标记

2. 代码解释器 (Code Interpreter)
   - 模型可以生成 Python 代码
   - 在沙箱环境执行并返回结果
   - 适用于: 数据分析、数学计算、图表生成

3. 函数调用 (Function Calling)
   - 与 OpenAI 兼容的 function calling 格式
   - 支持并行函数调用
   - 自动参数解析与类型匹配

4. 内置 CoT (Thinking Mode)
   - 模型可以在 <think> 标签中输出推理过程
   - 用户可以选择是否查看思维链
   - 对需要多步推理的复杂任务自动启用

示例:
  用户: "北京和上海谁的人口更多?"
  模型: <think>
        北京人口: 2189 万 (2024)
        上海人口: 2475 万 (2024)
        2475 > 2189
        所以上海人口更多
        </think>
        上海人口更多。根据 2024 年数据，上海人口约 2475 万，
        北京人口约 2189 万。
```

### 4.4 Tokenizer 进一步优化

Qwen2.5 对 tokenizer 做了进一步改进，虽然没有扩大词表大小（保持 152K），但优化了：
- 代码 token 的压缩率（对编程语言更高效）
- 多语言 token 的平衡（尤其是对阿拉伯语、俄语等非中英语言）
- 特殊 token 的处理（tool calls、thinking mode 等结构化输出）

## 第五章 Qwen3（2026 年，Apache 2.0）

### 5.1 最新进展

Qwen3 系列延续了 Qwen 的"全尺寸覆盖"策略，发布了三个主要规格：

| 模型 | 参数量 | 上下文 | 许可 |
|------|--------|--------|------|
| Qwen3-1.7B | 1.7B | 128K+ | Apache 2.0 |
| Qwen3-32B | 32B | 128K+ | Apache 2.0 |
| Qwen3-235B | 235B | 128K+ | Apache 2.0 |
| **Qwen3-Max-Thinking** | — | 128K+ | — |

### 5.2 Qwen3-Max-Thinking

Qwen3 的旗舰功能是 **Max-Thinking**——在 QwQ-32B 的推理能力基础上进一步升级。这是一个**端到端的推理增强系统**，整合了：
- 更长的推理链（在训练中支持数千步的 CoT 序列）
- 自我验证机制（模型对自己的推理步骤进行错误检查）
- 搜索增强推理（在推理过程中调用外部知识或工具）
- 多路径推理集成（从多个推理路径中选出最优结果）

### 5.3 全线 GQA

Qwen3 在所有尺寸上都统一采用 **GQA（Grouped Query Attention）**，包括最小的 1.7B 模型。这与 Qwen1 时代不同（Qwen1 的 7B 仅在部分层使用 GQA，小模型使用 MHA），标志着 GQA 已经成为现代 LLM 的标配。

### 5.4 架构统一

Qwen3 的另一个方向是 **架构统一**——所有尺寸共享相同的基本设计范式（GQA + SwiGLU + RMSNorm + RoPE），只在深度、宽度和专家数量上有差异。这使得：
- 技术栈复用（训练框架、推理优化可以在不同尺寸间共享）
- 蒸馏更容易（大模型的知识可以高效地蒸馏到小模型）
- 部署简化（一个推理引擎可以服务所有模型）

### 5.5 Qwen3.5 Plus（2026.02）：原生多模态旗舰

### 6.3 GQA 配置对比

| 模型尺寸 | Q Head 数 | KV Head 数 | GQA Ratio | 相对 MHA 的 KV Cache 节省 |
|---------|----------|-----------|-----------|------------------------|
| Qwen-7B | 28 | 4 | **7:1** | 85.7% |
| Qwen-14B | 40 | 8 | 5:1 | 80.0% |
| Qwen-72B | 64 | 8 | **8:1** | 87.5% |
| Qwen2-57B MoE | 16 experts, 4 active/token | — | — |

KV Cache 节省的计算：MHA 需要存储 n_Q 组 K 和 V，GQA 只需要存储 n_KV 组。以 7B（28Q/4KV）为例：

```
MHA 的 KV Cache 大小: 2 × 28 × head_dim × seq_len × dtype_size
GQA 的 KV Cache 大小: 2 × 4 × head_dim × seq_len × dtype_size
节省比例: (28 - 4) / 28 = 85.7%
```

这对推理部署的意义重大。72B 模型的 8:1 GQA 意味着 KV Cache 只需要 MHA 的 12.5%——在 128K 上下文场景下，这可能是 **"能不能部署"** 和 **"能不能负担部署成本"** 的区别。

## 第七章 关键技术深度解析

### 7.1 YARN——RoPE 的上下文扩展

标准 RoPE 的位置编码通过旋转矩阵嵌入相对位置信息。其核心公式为：

```
对于位置 p 和维度对 (2i, 2i+1):
  RoPE(p, 2i)   = cos(p·θ_i)
  RoPE(p, 2i+1) = sin(p·θ_i)

其中 θ_i = base^(-2i/d), base = 10000

每个维度 i 的波长: λ_i = 2π / θ_i = 2π · base^(2i/d)
  维度 i=0:   λ_0 ≈ 2π          (最短波长, 编码附近位置)
  维度 i=d/2: λ_{(d/2)} ≈ 2π·base  (中等波长)
  维度 i=d-1: λ_{(d-1)} ≈ 2π·base² (最长波长, 编码全局位置)
```

**问题**：当序列长度超过训练长度时，高维度的波长不够覆盖整个序列。具体来说：
- 如果训练长度是 32K，那么波长 > 32K 的维度可以正常编码
- 波长 < 32K 的维度会"绕圈"——同一个角度对应多个不同的位置
- 模型没有学会区分这些"重影"位置

**YARN 的解决方案**：

不是直接拉伸位置（线性插值），而是**调整每个维度的旋转频率**：

```
NTK-aware 缩放（YARN 的核心思想）:
  线性插值: p' = p / scale  (所有维度统一缩放)
    问题: 高频维度（短波长）的分辨率下降

  NTK-aware: θ'_i = θ_i · base^(-2i/d) → base' = base · scale^(d/(d-2))
    效果: 低频维度 → 大幅缩放（波长变长）
          高频维度 → 小幅缩放（保留分辨率）
    直觉: 高频维度"转得快"，位置间区分度高，不需要改太多
          低频维度"转得慢"，位置间区分度低，需要拉伸覆盖更远位置
```

YARN 的核心洞察是：**不需要对所有维度做相同的缩放。高频维度（短波长）天然擅长编码附近的相对位置，应该保留它们的分辨率；低频维度（长波长）负责编码全局位置，需要拉伸来覆盖更长的范围。**

### 7.2 DCA——高效长上下文注意力

Dual Chunk Attention 的完整实现细节：

```
训练时的 DCA 流程 (以 128K 序列为例):

1. 分块 (Chunking):
   输入序列 tokens [t₁, t₂, ..., t₁₃₁₀₇₂]
     ↓
   分成 16 块, 每块 8192 tokens
   chunk₁ = [t₁, ..., t₈₁₉₂]
   chunk₂ = [t₈₁₉₃, ..., t₁₆₃₈₄]
   ...
   chunk₁₆ = [t₁₂₂₈₈₀, ..., t₁₃₁₀₇₂]

2. 块内注意力 (层 l):
   for each chunk in [chunk₁, ..., chunk₁₆]:
       Q = chunk · W_Q  [8192, d]
       K = chunk · W_K  [8192, d]
       V = chunk · W_V  [8192, d]
       attn = softmax(Q·Kᵀ/√d) · V  [8192, d]
       # 每个 token 只能看到同一 chunk 内的其他 token
   # 复杂度: 16 × O(8192²) ≈ O(128K × 8K)

3. 跨块注意力 (层 l' > l, 每隔 N 层):
   # 在选定的层, 允许 token 跨 chunk 交互
   # 可以通过:
   a) 全局 token: 每个 chunk 的 [CLS] token 可以看所有 chunk
   b) 滑窗跨块: token 可以看相邻 2 个 chunk
   c) 全局注意力: 选定的层做完整 Full Attention
   # 这一层的计算复杂度退化为 O(L²)
   # 但因为只在少数层执行, 总体复杂度可控

4. 复杂度对比 (比率):
   Full Attention:            L²
   DCA (每层块内, N 层跨块):  L·C + (L²·N_selected)/N_total

   典型配置: C=8K, N_selected=2 (在 32 层中选 2 层做跨块)
   DCA 总复杂度 ≈ L·C + 2L²/32 ≈ L·8K + L²/16
   对比 Full Attention L²:
   当 L=128K: DCA ≈ 1.0×10⁹ vs Full ≈ 1.6×10¹⁰  → ~94% 节省
```

### 7.3 Qwen MoE 架构

Qwen2.5 的 236B MoE 是 Qwen MoE 技术的最高成就：

```
Qwen2.5-236B MoE 架构参数:
  ┌─────────────────────────────────────────────┐
  │  总参数量: 236B                              │
  │  激活参数量: 约 36-40B (取决于路由分布)      │
  │  每层专家数: 32                              │
  │  每 token 激活专家数: 6                      │
  │  Expert 类型: Fine-grained (细粒度)           │
  │  共享专家 (Shared Expert): 2 (在所有 token    │
  │    上都激活, 捕获通用知识)                    │
  │  Router: Top-6 routing + 负载均衡约束         │
  └─────────────────────────────────────────────┘

  架构设计选择:
    1. 细粒度专家 (Fine-grained Experts)
       - 不再是"每个专家是完整的 FFN"
       - 而是将 FFN 的隐层维度切分到多个专家上
       - 每个专家负责不同的"知识子空间"
       - 效果: 知识容量更大, 单个 token 可以利用更细粒度的组合

    2. 共享专家 (Shared Expert)
       - 2 个共享专家处理所有 token 都会用到的通用知识
       - 比如语法、常见词汇、基础推理模式
       - 减少路由负担（路由只需要分配"专用"知识）

    3. 容量因子 (Capacity Factor)
       - 设定每个专家能处理的最大 token 数
       - 防止某些专家过载导致 token 丢弃
       - 训练时容量因子 > 1 (允许过载), 推理时 = 1

  路由机制 (每层独立):
    输入 x → Router(x) → 与 30 个专家 (32 total - 2 shared) 计算匹配分数
      → 选择 Top-6 路由专家 + 强制激活 2 个共享专家 = 每 token 激活 8 个专家
      → 加权求和输出
```

**与 Mixtral 8×7B 的对比**：

| 维度 | Mixtral 8×7B | Qwen2.5-MoE |
|------|-------------|-------------|
| 总参数 | ~47B | 110B / 236B |
| 激活参数 | ~13B | ~22B / ~38B |
| 专家数 | 8 | 16 / 32 |
| 激活专家数 | 2 | 4 / 6 |
| 共享专家 | 无 | 有 |
| 细粒度专家 | 否 | 是 |
| 负载均衡 | Top-2 + Load Balance Loss | Top-N + 双 Loss |

Qwen 的 MoE 设计的核心思路是：**增加专家数量 + 采用细粒度切分 + 加入共享专家**，在推理计算量可控的前提下最大化模型的知识容量。
